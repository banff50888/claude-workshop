# Review of 2026-11-19 changes

Multi-agent review of all uncommitted changes in the working tree: dark mode and the Light/Dark selector, Simplified Chinese, the Shipments feature (data, API, page), the SQLite storage layer, the Redis order cache and its list/clear endpoints and Orders page section, the Dockerfile and the Docker build workflow.

## How it was done

- Six reviewers, one per area (backend-db, backend-api, tests, frontend-pages, frontend-theme-i18n, infra), each covering correctness and security. All were read-only.
- Each finding was then checked by a separate verifier whose job was to refute it. Severities below are the verifier's, not the reviewer's: four findings the reviewers rated medium were lowered to low.
- 20 findings in total: 15 confirmed, 5 rejected.
- Seven issues from an earlier quick code review were excluded so they would not be reported twice. They are listed at the end and are still open.

## Confirmed findings

Only one confirmed finding is medium. The rest are low.

### Medium

| Area | Location | Finding |
|---|---|---|
| frontend-theme-i18n | `client/src/views/Inventory.vue:102` | In Japanese and Chinese, the views put a `¥` in front of the raw USD amounts without converting them. `utils/currency.js` converts (about 150x for JPY, 7x for CNY), so the same amount shows as `¥1,000` in some views and `¥7,000` in others. `Spending.vue`, `ProductDetailModal.vue` and `InventoryDetailModal.vue` use the same pattern. The JPY case was already like this before today. |

### Low

**backend-db**
- `server/data/shipments.json`: `orders.json` has duplicate ids and order numbers for orders 201-210. 20 shipments (not 10) point at an ambiguous order id. `GET /api/orders/205` can only return the first match. Each shipment carries its own customer, warehouse, category and order date, so the page still renders correctly. The duplicates themselves were in the original data.
- `server/db.py:167,170`: SQLite `LOWER()` only folds ASCII, while the old in-memory filter used Python's `.lower()`. No effect on the current ASCII data.

**tests**
- `tests/backend/conftest.py:10`: the tests don't isolate the database or Redis. They run against the real `server/data/factory.db`, and against a real Redis if one is running at `localhost:6379`. Fix: set `FACTORY_DB_PATH` to a temp path and `CACHE_ENABLED=0` in `conftest.py` before importing `main`, because both modules read the environment at import time.
- `tests/backend/test_shipments.py:70`: `test_get_shipments_by_month` and `test_get_shipments_multiple_filters` loop over the response without checking it is non-empty, so an empty result would pass. The data has 23 shipments in 2025-03 and 24 for London/Sensors/Delivered.
- `tests/backend/test_orders_cache.py` (around line 232): `test_list_ignores_non_order_keys` has no non-empty assertion and doesn't check that `inventory:all` is absent. The reviewer overstated the risk, since another test covers an always-empty list.
- `tests/backend/test_orders_cache.py` (around line 184): `test_works_when_redis_is_down` only compares two 200 responses. It doesn't check that the failure path ran or that the circuit breaker engaged. Recovery after the retry interval, TTL expiry and a corrupt cached value are untested.

**frontend-pages**
- `client/src/views/Shipments.vue:121`: the global Order Status filter is sent to `/api/shipments`, where the values don't match. Only "Delivered" overlaps with the shipment statuses (In Transit, Out for Delivery, Preparing, Delayed, Delivered). Picking Shipped, Processing or Backordered gives an empty table. The page has no status filter of its own. "All" works.
- `client/src/views/Shipments.vue:123`: `loadShipments` has no request sequencing, so out-of-order responses can show stale data after quick filter changes. Unlikely, since the API is fast.
- `client/src/views/Orders.vue:201`: `formatDate` has no `pt_BR` mapping and falls back to en-US, while Shipments uses `pt-BR`, so the two pages format Portuguese dates differently. The gap in Orders was there before today.

**frontend-theme-i18n**
- `client/src/composables/useI18n.js:23`: the saved locale isn't validated and the `localStorage` calls have no `try/catch`, unlike `useTheme.js`. An unknown saved value falls back to English. The app fails to start only where storage access throws. This predates today's changes.
- `client/src/utils/currency.js:10`: `pt_BR` maps to BRL, but the currency functions only handle JPY and CNY, so Portuguese users see USD values and `$K` on Dashboard charts.
- `client/src/composables/useI18n.js:18`: every `zh*` browser language, including Traditional Chinese (`zh-TW`, `zh-HK`), is mapped to Simplified Chinese with CNY. `useAuth.js` still has no Portuguese profile data, so `pt_BR` users see English profile and task data.

**infra**
- `.github/workflows/docker-build.yml:22`: the actions are pinned to mutable version tags, and the job has `packages: write`. Push and login are already limited to push events. Pin the actions to commit SHAs for hardening.
- `.github/workflows/docker-build.yml:6`: the `pull_request` trigger doesn't include the workflow file itself, so a PR that only edits the workflow won't run it. The `push` trigger does include it.

## Rejected findings

| Area | Claim | Why it was rejected |
|---|---|---|
| tests | Shipment filter tests don't prove filters narrow the result. | Each filter test asserts every returned item matches the filter, and the data covers several values, so a no-op filter would fail. The one valid point (no non-empty check on the month test) is listed above. |
| tests | The SQLite-versus-in-memory comparison uses a weak query parser and compares against its own source. | The fixed test queries never need decoding, and the same raw values reach both sides. Comparing against the JSON is the intended check, and it would catch seed regressions. |
| frontend-pages | A shipment with a missing estimated delivery would show "ETA -". | The API model requires `estimated_delivery` and all 214 records have it, so a missing value can't reach the UI. |
| infra | `requirements.txt` uses unpinned `>=` bounds, and the image has no Redis service or health check. | The same bounds are in `pyproject.toml`, the cache fails open, and the rest are design choices, not defects. |
| infra | `.dockerignore` doesn't exclude SQLite `-wal`/`-shm` files or `.env`. | No WAL mode is used, and the Dockerfile copies only named files plus `data/`, so a `.env` is never copied. |

## Coverage and limits

- `backend-api` (`cache.py`, `main.py`, the new routes) returned no new findings. That review was short (3 tool calls). The earlier quick review had covered the same files.
- The reviewers took a short pass each (2-7 tool calls). The dark-mode conversion of individual components was only spot-checked.
- No real Redis server was available in this environment. All cache behaviour was tested against a fake client only.
- The 5 rejected claims were each checked by one verifier, not a panel.

## Issues from the earlier quick review (still open)

1. `db.seed()` only fills empty tables, so edits to the JSON files are ignored once `factory.db` exists (`uv run python db.py --reset` rebuilds it). `server/CLAUDE.md` still says a restart reloads from the files.
2. SQLite connections opened with `with connect() as conn` are never closed.
3. `cache.get_json` calls `json.loads` outside the `try`, so a corrupt cached value gives a 500. `CACHE_TTL_SECONDS=0` makes every cache write fail and disables the cache for 30 seconds each time.
4. Order cache keys aren't normalized, so `Sensors` and `sensors` get separate entries, and so do an empty month and no month.
5. The Redis client state in `cache.py` has no lock, so several threads can retry the connection at once.
6. `/api/orders` reads SQLite per request, while the dashboard, reports and shipments endpoints use lists loaded at startup.
7. `DELETE /api/cache/orders` has no authentication, and its `order` prefix would also match future keys that start with `order`.
